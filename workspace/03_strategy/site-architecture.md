# Financeable Consulting Site Architecture

## Positioning

Financeable Consulting is a finance consultancy, not an SEO product. The public site should lead with service clarity, commercial credibility, and conversion. The larger SEO landing-page system should support later expansion, not dictate the live site structure.

## Live site scope

The publishable website should contain six core pages:

- Home
- Monthly CFO
- Financial Reporting
- Cashflow Management
- About
- Contact

These pages are the public launch scope. The 450-page matrix remains a separate expansion backlog.

## Page model

Each row in the matrix represents one keyword-location page.

Recommended page families:

- Core service pages
- Commercial/service-intent pages
- Deliverable pages
- Informational pages
- Audience pages
- Comparison pages

## Content standard

Every production page should follow one reusable master template.

- Target length: `1,500` words
- Hero section includes a contact form
- Q&A section appears at the end of the page
- Copy is written in English
- Each page is optimized for both classic search and AI-search retrieval
- Service pages should be written to stand alone without relying on surrounding navigation for context

## Public launch URL logic

Use clean brand-site URLs for the six live pages:

- `/`
- `/services/monthly-cfo/`
- `/services/financial-reporting/`
- `/services/cashflow-management/`
- `/about/`
- `/contact/`

## SEO expansion URL logic

Use flat keyword-location slugs for later landing pages where possible.

Examples:

- `/monthly-cfo-london`
- `/fractional-cfo-london`
- `/financial-reporting-city-of-london`
- `/cash-flow-forecasting-manchester`
- `/finance-support-southwark`

## Rollout order

- `Launch site`: publish the six-page Financeable Consulting website first
- `P1`: London landing pages only
- `P2`: Manchester plus strongest central-London district pages
- `P3`: remaining district expansion and lower-intent informational coverage

## Parent cluster logic

Parent slugs in the matrix indicate the hub page each child page should connect to. This supports internal linking and keeps service clusters coherent during rollout.
